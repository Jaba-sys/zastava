# MyPeal

Мессенджер (веб) на React + Firebase: регистрация с подтверждением по email,
уникальные теги (@username), заявки в друзья, чаты в реальном времени,
базовая админка.

Проект Firebase: **mymessage-73c49** (создан и настроен: Email/Password auth,
Firestore, конфиг веб-приложения уже вписан в `web/.env`).

## Структура

```
mymessage/
  web/         — React (Vite) фронтенд
  functions/   — Cloud Functions (Node.js) — бэкенд-логика
  scripts/     — скрипт создания админ-аккаунта
  firestore.rules, firestore.indexes.json, firebase.json — конфиг Firebase
```

## Что уже реализовано (MVP)

- Регистрация: email + пароль + повтор пароля
- 5-значный код подтверждения на почту (генерируется и отправляется
  Cloud Function `onUserCreate`, письмо шлётся через Gmail SMTP)
- Ввод кода, повторная отправка с ограничением частоты (раз в минуту)
- Выбор уникального тега `@tag`, с проверкой занятости и подсказкой
  свободных вариантов (`tag1234` и т.п.), если занято
- Профиль: имя (обязательно), описание и дата рождения (необязательно)
- Поиск людей по тегу, отправка заявки в друзья, принятие/отклонение
- Чат 1-на-1 в реальном времени (Firestore)
- Админ-аккаунт с флагом `isAdmin`, простая админ-панель: список всех
  пользователей, блокировка (с причиной и датой окончания или навсегда)
  и разблокировка

## Что ещё предстоит (Фаза 2 — не входило в MVP этой сессии)

- **Лимит устройств (макс. 3)** и системные сообщения о новом входе с
  кнопкой "выйти с того устройства" — требует таблицы активных сессий
  (`users/{uid}/devices/{deviceId}`) с fingerprint/refresh-token и
  Cloud Function, которая при новом входе проверяет количество активных
  устройств, создаёт системное сообщение и умеет принудительно
  отзывать refresh-токены конкретного устройства
  (`admin.auth().revokeRefreshTokens`)
- **Автоматическая очистка старой переписки при заполнении базы** —
  в реальности Firestore не даёт простого API "сколько места осталось"
  внутри Cloud Function; правильный вариант — периодическая
  (scheduled) функция, которая через Cloud Monitoring API проверяет
  объём хранилища проекта и, при превышении порога, удаляет самые
  старые сообщения (пачками, начиная с `chats/*/messages` с наименьшим
  `createdAt`), либо более простой вариант — держать лимит N последних
  сообщений на чат
- **Более строгая проверка банов** — сейчас блокировка проверяется по
  полю `banned` в документе пользователя (клиент + security rules).
  Для полной защиты (например, блокировки чтения) стоит переключиться
  на custom claims (`admin.auth().setCustomUserClaims`), обновляемые
  Cloud Function-триггером при изменении `users/{uid}.banned`
- Push/звуковые уведомления, статусы "прочитано", медиа-вложения,
  групповые чаты — по вашему запросу

## Деплой — через GitHub Actions

Сайт деплоится автоматически при каждом push в ветку `main` — через
`.github/workflows/deploy.yml`. Firestore-правила уже опубликованы
вручную через Firebase Console и отдельного деплоя не требуют.

Перед первым push добавьте в репозитории (Settings → Secrets and
variables → Actions → New repository secret) следующие секреты:

| Имя секрета | Значение |
|---|---|
| `FIREBASE_SERVICE_ACCOUNT` | содержимое JSON-файла service account key целиком (Firebase Console → Project settings → Service accounts → Generate new private key) |
| `VITE_FIREBASE_API_KEY` | из `web/.env.example` / Firebase Console → Project settings |
| `VITE_FIREBASE_AUTH_DOMAIN` | — // — |
| `VITE_FIREBASE_PROJECT_ID` | — // — |
| `VITE_FIREBASE_STORAGE_BUCKET` | — // — |
| `VITE_FIREBASE_MESSAGING_SENDER_ID` | — // — |
| `VITE_FIREBASE_APP_ID` | — // — |

После этого сайт будет доступен по адресу **https://mypeal.web.app**.

Это отдельный Hosting-сайт внутри того же Firebase-проекта (Firebase
позволяет несколько сайтов на проект, бесплатно даже на Spark-плане) —
завели его специально, чтобы адрес не включал автосгенерированный
`-73c49` от ID проекта. Куда именно деплоится сайт, задаётся полем
`"site"` в `firebase.json`. Старые адреса — `mymessage-73c49.web.app`
(дефолтный сайт проекта) и `jaba-mymessage.web.app` (первая попытка
имени без `-73c49`) — тоже продолжают существовать, но больше не
обновляются автодеплоем. Ненужные можно удалить в Firebase Console →
Hosting → выбрать сайт в выпадающем списке "site: ..." → ⋮ → Delete
site.

## Создание админ-аккаунта

Два способа — любой:

**Через GitHub Actions (без установки чего-либо):** добавьте секреты
`ADMIN_EMAIL` и `ADMIN_PASSWORD` (кроме `FIREBASE_SERVICE_ACCOUNT`,
он уже нужен для деплоя выше), затем во вкладке **Actions** выберите
workflow **"Create/update admin account"** → **Run workflow**.

**Локально:**

```bash
cd scripts
npm install firebase-admin
# положите сюда serviceAccountKey.json (Firebase Console → Project
# settings → Service accounts → Generate new private key) — этот файл
# в .gitignore, никогда его не коммитьте
ADMIN_EMAIL='you@example.com' ADMIN_PASSWORD='ваш-пароль' node seedAdmin.js
```

Создаст/обновит аккаунт с тегом `@admin` и правами администратора,
сразу с подтверждённой почтой (без перехода по ссылке).

## Транспорт Firestore (скорость доставки)

Подписки Firestore по умолчанию идут через WebChannel — один открытый поток.
Это самый быстрый путь, и от него зависят и доставка сообщений, и звонки:
обмен offer/answer/ICE идёт через те же подписки, поэтому тормозящий
транспорт выглядит как "нажал ответить, висит «Соединяем…», звонок
сбросился по таймауту".

На части устройств поток молча не поднимается (у нас — iPhone/Safari):
приложение работает из кэша, но новые сообщения не приходят, а свои висят в
локальной очереди. Лечение — long-polling, но он заметно медленнее.

Поэтому в `web/src/firebase.js` автоопределение long-polling включается
**только на iOS**. На всех остальных платформах остаётся быстрый поток. Если
когда-нибудь такая же жалоба придёт с другой платформы, добавляйте её в
`isAppleMobile()` точечно, а не включайте автоопределение всем подряд.

## Групповые звонки

В группах есть звонок на несколько человек (`web/src/contexts/
GroupCallContext.jsx`, `firestore.rules` → `groupCalls/{callId}`). Личные
звонки (`CallContext.jsx`) остались как были — это отдельный механизм.

Модель — "комната + дозвон", как в Telegram:

- тот, кто начинает звонок, выбирает, кому звонить: всю группу сразу
  ("Выбрать всех") или отдельных людей;
- выбранным приходит обычный входящий вызов;
- звонок при этом живёт как комната: остальные участники группы видят в
  чате плашку "Идёт групповой звонок · присоединиться" и могут зайти
  позже сами, даже если им не звонили;
- прямо во время разговора можно дозвониться ещё кому-то (кнопка
  "Добавить");
- когда выходит последний участник, звонок закрывается и в чат
  добавляется заметка.

**Кто может звонить.** По умолчанию — только владелец группы. Он может
разрешить это всем участникам: ⚙ (управление группой) → "Кто может
начинать звонки" → "Разрешить всем". Это поле `chats/{chatId}.
callByMembers`, и его же проверяют правила Firestore — не только интерфейс.

**Ограничения.** Бэкенда нет, поэтому звук идёт "каждый с каждым" (mesh):
в звонке из N человек у каждого N-1 соединений. Отсюда потолки в
`web/src/utils/groupCalls.js`:

- `MAX_PARTICIPANTS = 20` — жёсткий предел на звонок;
- `MAX_VIDEO_PARTICIPANTS = 6` — выше этого кнопка камеры не показывается:
  видео в mesh дороже голоса примерно на порядок. Само право включать
  камеру — та же платная функция, что и в личных звонках
  (`videoCallUnlocked`).

Сигнализация: на каждую попытку соединения пары создаётся документ в
`groupCalls/{callId}/conns` (id автоматический — человек может выйти и
зайти снова, и тогда ему нужно новое соединение, а не переписанный старый
документ). Offer пишет тот, чей uid меньше, answer — второй; ICE-кандидаты
лежат в `aCandidates`/`bCandidates` и каждая сторона пишет только свою.

**Живость участников.** Каждый в звонке раз в 30 секунд обновляет свою
отметку `groupCalls/{callId}/presence/{uid}`. Если отметка молчит больше
90 секунд (вкладку закрыли, связь пропала), "призрака" вычищают из звонка:
это делает либо кто-то из самого звонка, либо — если живых там уже не
осталось — любой участник группы, у кого открыт чат; последний протухший
закрывает звонок целиком. Без этого закрытая вкладка оставляла бы группе
вечную плашку "идёт звонок": правила разрешают убрать из `participants`
только самого себя. Отметки лежат отдельными документами, чтобы не
переписывать сам звонок каждые полминуты — иначе его снапшот летел бы всем
участникам и всем, у кого открыт чат группы.

**Не забудьте про индексы.** Новые запросы требуют составных индексов —
они уже описаны в `firestore.indexes.json` (`groupCalls`: `invited` +
`status` и `chatId` + `status` + `createdAt`). Если их не опубликовать
(`firebase deploy --only firestore:indexes` или по ссылке из ошибки в
консоли браузера), входящие групповые вызовы просто не будут приходить.

## Неподтверждённая почта = аккаунта нет

Пока человек не подтвердил почту, аккаунт в базе **не создаётся**:

- регистрация создаёт только запись в Firebase Auth и отправляет письмо,
  документ `users/{uid}` не пишется вообще;
- профиль появляется в тот момент, когда человек перешёл по ссылке из
  письма (`web/src/pages/VerifyEmail.jsx`);
- анти-абьюз "один аккаунт на браузер" (`deviceRegistrations`) проверяется
  по-прежнему сразу при регистрации, до отправки письма; если регистрацию
  бросили и аккаунт удалили, отметка снимается вместе с ним;
- то же самое правило продублировано на сервере: `firestore.rules` →
  `users/{uid}` **create** разрешён только при `email_verified == true`
  в токене (или с валидным одноразовым админским ключом `emailKeys`);
- значит, неподтверждённый человек не виден в поиске, не может писать,
  не появляется в админке и не занимает места в базе.

Сам Auth-аккаунт какое-то время всё же существует — иначе ссылку из
письма было бы некому подтверждать — и удаляется:

- сразу, если нажать "Отменить регистрацию" на экране подтверждения;
- при следующей попытке входа, если почта всё ещё не подтверждена, а с
  момента создания прошло больше часа (`UNVERIFIED_GRACE_MS` в
  `web/src/utils/pendingAccounts.js`), — email тут же освобождается;
- пачкой через workflow **"Purge unverified accounts"**
  (`scripts/purgeUnverified.js`) — для тех, кто просто закрыл вкладку и
  не вернулся. Тот же скрипт снимает "осиротевшие" отметки устройств,
  оставшиеся от уже удалённых аккаунтов. По умолчанию workflow только
  показывает список; чтобы реально удалить, переключите вход `apply` в
  `true`.

Аккаунты, подтверждённые админским ключом (`verified: true` в Firestore
при `emailVerified: false` в Auth), ни один из этих механизмов не
трогает.

## Удаление аккаунта

В самой админ-панели сайта кнопки "Удалить" нет — там только
блокировка (`banned`), потому что настоящее удаление должно сносить
и запись в Firebase Auth (иначе человек по-прежнему сможет войти), а
это доступно только через Admin SDK, то есть через тот же workflow,
что и создание админа.

**Через GitHub Actions:** вкладка **Actions** → workflow **"Delete
user account"** → **Run workflow** → введите email аккаунта, который
нужно удалить.

Скрипт (`scripts/deleteAccount.js`) удаляет:

- сам аккаунт в Firebase Auth (по этому email больше нельзя войти);
- документ `users/{uid}`;
- его тег в `tags/{tag}` (тег освобождается и его снова можно занять);
- все его заявки в друзья (отправленные и полученные);
- все чаты, в которых он состоял, вместе со всеми сообщениями в них.

Действие необратимо. Аккаунты с правами администратора (`isAdmin:
true`) скрипт удалять отказывается — это защита от случайного
самоудаления; чтобы всё-таки удалить такой аккаунт, сначала вручную
снимите права через Firebase Console (Firestore → `users` → нужный
документ → `isAdmin: false`), затем запустите workflow.

**Локально** — так же, как `seedAdmin.js` (см. выше), но:

```bash
cd scripts
npm install firebase-admin
TARGET_EMAIL='user@example.com' node deleteAccount.js
```

## Безопасность

- Никакой бизнес-логики на клиенте, которой можно доверять "на слово" —
  всё проверяется на сервере через `firestore.rules` (единственный
  реальный источник защиты, раз Cloud Functions не используются):
  кто что может читать/писать, что можно менять только себе, что тег
  уникален, что админ-права/бан/подтверждение нельзя выставить себе
  самостоятельно и т.д. Смотрите `firestore.rules` — это по сути
  документ, описывающий модель доступа.
- Подтверждение почты — через встроенный механизм Firebase Auth
  (`email_verified` в самом токене, подделать нельзя со стороны клиента).
- Секреты никогда не попадают в репозиторий: `.gitignore` исключает
  `functions/.env` (Gmail app password), `web/.env` (конфиг Firebase —
  не секрет сам по себе, но не коммитим по умолчанию) и
  `scripts/serviceAccountKey.json` (полный доступ к проекту). Вместо
  них в репозитории лежат `*.env.example` с плейсхолдерами.
- Пароль администратора нигде не хранится в коде — только передаётся
  через переменную окружения при разовом запуске `seedAdmin.js`.
- Firebase Web API key в `web/.env` — не секрет в привычном смысле (он
  всё равно виден в бандле браузера), реальная защита данных — это
  правила Firestore выше, а не сокрытие этого ключа.

## Модель данных Firestore

- `users/{uid}` — email, name, bio, birthdate, tag, verified, isAdmin,
  banned, banReason, bannedUntil, profileComplete
- `tags/{tag}` — { uid } — резервация уникальных тегов
- `pendingVerifications/{uid}` — код подтверждения, срок действия,
  количество попыток (недоступно клиенту)
- `friendRequests/{id}` — from, to, status (pending/accepted/declined)
- `friends/{uid}/list/{friendUid}` — список друзей
- `chats/{chatId}` — members, lastMessage, updatedAt
- `chats/{chatId}/messages/{id}` — text, senderId, createdAt
